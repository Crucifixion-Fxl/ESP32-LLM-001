# v1.0.0 — Seven-board ESP32-S3 LLM cluster

Experimental Qwen2-0.5B inference across one master and six ESP32-S3 compute
nodes. This release provides the firmware and model binaries needed to reproduce
the seven-board setup.

Start with the [English setup and wiring guide](https://github.com/Crucifixion-Fxl/ESP32-LLM-001/blob/main/docs/getting-started.md).

## Included assets

| Archive | Contents | Flash addresses |
| --- | --- | --- |
| `firmware-master.zip` | Master firmware, bootloader and partition table; sampling temperature 0.4, up to 64 generated tokens, and invalid-frame diagnostics | Bootloader `0x0`; partition table `0x8000`; application `0x10000` |
| `firmware-node.zip` | Compute-node firmware, bootloader and partition table; corrected Xtensa MAC kernel and 64 boot-time lane comparisons | Bootloader `0x0`; partition table `0x8000`; application `0x10000` |
| `model-bins.zip` | `tokenizer.bin`, `embed.bin`, `final_norm.bin` and six four-layer binaries | Master: `0x90000`, `0x150000`, `0xFF0000`; each node: `0x90000` |

All boards require **ESP32-S3 N16R8**: 16 MB flash and 8 MB octal PSRAM.
Extract the two firmware archives separately to avoid mixing their partition tables.

## Model and training

- Base model: Qwen2-0.5B, 24 transformer layers, vocabulary cropped to 32,000.
- Linear weights: ternary (`−1, 0, +1`), stored as two-bit codes.
- Embeddings: INT4.
- Training: 4,000 steps on WikiText-103, with simulated firmware INT8 activation quantization.
- Reported validation loss: **4.58**; perplexity: **97.8**.

## Quick start

Install the flashing tool:

```bash
python3 -m pip install esptool
```

Replace `PORT` with the connected board's serial port. Flash one board at a time
with reset-cascade links disconnected. Run each command from the extracted
folder containing its input files, or use explicit paths.

### Master

From the extracted master firmware folder:

```bash
python3 -m esptool --chip esp32s3 --port PORT --baud 921600 write-flash \
  0x0 bootloader.bin 0x8000 partition-table.bin 0x10000 master_board.bin
```

From the extracted model folder:

```bash
python3 -m esptool --chip esp32s3 --port PORT --baud 2000000 write-flash \
  0x90000 tokenizer.bin 0x150000 embed.bin 0xFF0000 final_norm.bin
```

### Nodes 1–6

From the extracted node firmware folder, flash each node with:

```bash
python3 -m esptool --chip esp32s3 --port PORT --baud 921600 write-flash \
  0x0 bootloader.bin 0x8000 partition-table.bin 0x10000 node_board.bin
```

Then, from the model folder, flash that node's layer file. For Node 1:

```bash
python3 -m esptool --chip esp32s3 --port PORT --baud 2000000 write-flash \
  0x90000 layers_0_to_3.bin
```

| Node | Model file |
| --- | --- |
| 1 | `layers_0_to_3.bin` |
| 2 | `layers_4_to_7.bin` |
| 3 | `layers_8_to_11.bin` |
| 4 | `layers_12_to_15.bin` |
| 5 | `layers_16_to_19.bin` |
| 6 | `layers_20_to_23.bin` |

Power off before wiring the cluster. Follow the [wiring reference](https://github.com/Crucifixion-Fxl/ESP32-LLM-001/blob/main/docs/architecture.md#wiring),
including the Node 6 → Master return hop, reset cascade, ready signal and common
ground. Open the master USB serial console at 115200 baud, wait for readiness,
then enter a short prompt and press Enter.

## Kernel correction relative to upstream

The original experiment traced incorrect weight-lane loading to the use of
`ee.movi.32.q` in `bitlinear_forward_q.S`, with 75% of weights reported as not
participating in the intended calculation. This version rewrites the sequence
using one word in each of eight registers and four `vmulas` operations.

The development notes report approximately **1.04 seconds per four-layer node**
for 55.6 million MACs. See the [original investigation (Chinese)](https://github.com/Crucifixion-Fxl/ESP32-LLM-001/blob/main/docs/development-notes.zh-CN.md)
for the diagnostic evidence and context.

## Reported results and limitations

The original setup reported approximately **7 seconds per token**, about **1.2 W
idle** and **1.5 W during generation**. These are historical experiment results,
not benchmarks rerun when release text or repository documentation changes.

- Generated text may repeat or be incoherent.
- Return-link corruption and long first-token stalls were observed in the original setup.
- The 64 boot diagnostics print ASM/C++ comparisons; they do not assert or halt on a mismatch.
- Host packed-weight validation does not emulate all firmware numerics, including INT8 activations.

This English release-note revision updates the description and documentation
links only. The original release tag and three binary attachments are unchanged;
no new on-board validation is claimed.
